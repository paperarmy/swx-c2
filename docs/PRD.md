# SWx-C2 PRD v2.3 (교육기간 구현용)

Oct 3, 2026 · @태옥 · **v2.3 개정 Oct 9, 2026**

> v2.1에서 문서 안의 불일치를 모두 정리했다(변경 내역은 부록 C). 이제 장 사이에 우선순위 규칙이 필요 없으며, 이 문서 자체가 단일 기준이다. 진행 상태와 결정 로그는 `docs/CURRENT_STATUS.md`에 둔다.

## 1. 개요와 성공 기준

교육 기간(3일차 오후~4일차, 실작업 약 10시간) 안에 **공개 데이터로 실제 동작하는 우주기상 지휘통신 영향판단 보드를 배포**하고, 전구 적용 방향성을 설득하는 것이 목표다. 기획 배경과 R/S/G 설명은 별도 기획서를 따른다.

**심사 초점 가정**: 완성도보다 가능성, 구현가능성, 방향성. 따라서 기능 수를 늘리기보다 "핵심 흐름이 실데이터로 끊김 없이 돈다"를 증명하는 데 집중한다.

| 심사 관점 | 증명 방법 | 성공 기준 |
| --- | --- | --- |
| 가능성(문제·가치) | 연합연습 등 대부대 훈련에서도 반복 논의되는 사례, 1967년 레이더 교란 사례 | 청중이 30초 안에 문제를 이해 |
| 구현가능성 | 공개 실데이터 연동 + 배포된 URL + 규칙 파일 구조 | 발표장에서 실시간 데이터로 동작 |
| 방향성(확장) | 재현 모드, 국방망 이식 경로, 단계별 로드맵 | "다음 단계가 무엇인지" 명확히 제시 |

**핵심 흐름(반드시 동작)**: 데이터 수집 → R/S/G 등급 산출 → 한반도 주·야간 반영 → 체계별 영향 단계 → PACE 권고 표시. 여기에 **AI 장차 전망(D+1~27 지자기 위험 확률)**을 더한다.

**확정 사항**
- 작전 조치 기준선은 3등급.
- 작전영향 등급 명칭은 **정상 · I 관찰(1~2등급) · II 대비(3등급) · III 조치(4~5등급)**. 국가 위기경보 명칭(관심·주의·경계·심각)은 쓰지 않는다(12.1).
- AI 장차 전망은 **Must**. 사전 학습한 로지스틱 회귀를 브라우저에서 계수로 계산한다. ML이 기준선을 못 이기는 구간은 27일 재귀 기준선을 표시하므로 탭6은 어느 경우에도 완성된다(5.4).
- 진행 상태·인계·결정 로그는 `docs/CURRENT_STATUS.md` 하나로 관리한다(9장).
- 교육 목적으로 **Supabase 로그인·사용자 승인**을 넣는다(P1.5). 역할은 사용자·관리자 2단계, 승인된 사용자만 열람한다. PRD 11.9의 축소판이며 P9에서 3단계 역할·MFA·감사 로그로 확장한다.
- 개발 도구는 VS Code + Claude Code(Opus 5.5).

**두 개의 트랙**: 교육 트랙(P0~P6)은 발표용 1차 완성본을, 고도화 트랙(P7~P13, 11장)은 교육 이후 실제 시범운용이 가능한 체계를 목표로 한다. 교육 트랙의 설계 원칙(데이터 입구 1개, 규칙 파일 분리, 엔진 순수 함수)은 고도화에서도 그대로 유지해 다시 만들지 않고 확장한다.

## 2. 범위

교육 기간에는 Must 6개만 완성하고, Should는 시간이 남을 때, Later는 발표의 로드맵으로만 다룬다.

| 구분 | 기능 | 비고 |
| --- | --- | --- |
| Must | R/S/G 현재 등급·3일 예보 수집 | NOAA, 인증키 불필요 |
| Must | 한반도 주·야간 판정 | 천문연 출몰 API, 실패 시 내장 계산 |
| Must | 규칙 기반 판단 엔진(rules.json) | 임계값은 코드가 아닌 설정 파일. 출처 태그·SRB·저궤도 토글 포함(12.3) |
| Must | 탭1 지휘관 브리핑, 탭2 영향 매트릭스, 탭3 PACE 권고 | 근거 규칙 표시 포함 |
| Must | 탭5 과거 사례 재현(2024년 5월) | 시연 핵심 |
| Must | 탭6 AI 장차 전망: 향후 1~27일 지자기 위험 확률 | P0 사전 학습, 브라우저는 계수로 계산만. ML이 기준선 미달 구간은 27일 재귀로 표시. 5.4 참조 |
| Must | 로그인·가입 승인·사용자 관리(Supabase, 사용자·관리자) | P1.5. 권한은 RLS·DB 함수에서 강제 |
| Should | 장기 기저확률(태양주기 위상·계절) | 플레어처럼 장기 예측이 안 되는 현상용 |
| Should | 탭4 장애 원인 판별(우주기상 vs 재밍) | 질문 3~4개짜리 체크 |
| Should | 용어 도움말(6.4) | glossary.json |
| Should | 한·영 병기 브리핑 문구 | 연합 활용성 강조 |
| Should | 우주환경센터 경보·국가 위기경보 병기 | API 확인 시. 없으면 "미연동" 표기 |
| Later | 지속·반복 상향, 해제 규칙(이력 필요, 12.3), 한반도 TEC·국내 지자기 보정, 플레어 목록 기반 R 확률 정밀화, 전망 모델 확장 평가(12.4), 실운용 고도화(11장) | 로드맵 슬라이드 |

**하지 않는 것**: 우주기상 데이터의 DB 저장·이력 축적(고도화 P8), 3단계 역할·MFA·감사 로그(고도화 P9), 서버 측 AI 추론·대형 모델(딥러닝 등 브라우저에서 계수로 계산할 수 없는 모델), 실제 장비 제원 입력, 군 내부 데이터 사용.

### 3.2 내부 표준 스키마(SwxState)

화면과 판단 엔진은 이 구조만 알면 된다. 실시간·재현 모드도 같은 구조를 쓴다.

```json
{
  "asOfUtc": "2026-10-12T05:00:00Z",
  "mode": "live",
  "scales": { "R": 1, "S": 0, "G": 2 },
  "forecast": [ { "dateUtc": "2026-10-13", "R12pct": 25, "R35pct": 5, "S1pct": 5, "Gmax": 3 } ],
  "kpForecast": [ { "timeUtc": "2026-10-12T06:00:00Z", "kp": 5.67 } ],
  "metrics": { "xrayFlux": 1.2e-5, "xrayClass": "M1.2", "protonPfu": 3.1, "kp": 5.33 },
  "korea": { "lat": 36.35, "lon": 127.38, "isDaytime": true, "sunriseKst": "06:31", "sunsetKst": "18:02", "sunSource": "builtin" },
  "srb": { "active": false, "lastAlertUtc": null, "events": [ { "productId": "TIIA", "issuedUtc": "2026-10-12T03:30:00Z", "title": "ALERT: Type II Radio Emission" } ] },
  "history": {
    "dailyMaxKp": [ { "dateUtc": "2026-08-14", "kp": 3.33 } ],
    "sn27": 120.5,
    "f107_27": 150.2
  },
  "series": {
    "xray": [ { "timeUtc": "2026-10-12T04:50:00Z", "flux": 1.2e-5 } ],
    "kp": [ { "timeUtc": "2026-10-12T03:00:00Z", "kp": 5.33 } ]
  },
  "outlook": [ { "dateUtc": "2026-10-19", "h": 7, "pG1": 0.34, "pG3": 0.04, "basis": "ml" } ],
  "outlookSkill": { "bssVsClimatology": 0.12, "bssVsRecurrence": 0.03, "byHorizon": { "1-3": 0.2, "4-13": 0.05, "14-27": 0.02 }, "validPeriod": "2020-2026" },
  "rBaseline": { "pR3PerDay": 0.03, "basis": "climatology" },
  "sources": [ { "id": "D1", "ok": true, "fetchedAtUtc": "2026-10-12T05:00:10Z" },
               { "id": "D7", "ok": false, "fetchedAtUtc": null, "note": "인증키 없음, 내장 계산 사용" } ]
}
```

이 스키마가 단일 기준이다. 5.4의 출력 형식은 이 중 `outlook`·`outlookSkill`·`rBaseline` 부분을 설명한 것이다. `mode`는 `live`, `fallback`, `replay` 중 하나다. `history.dailyMaxKp`는 최근 60일을 담는다. 숫자는 모두 형식 예시다.

- `outlook`·`outlookSkill`·`rBaseline`은 `/api/swx`가 아니라 브라우저의 `forecast.js`가 `history`로 계산해 채운다. 서버는 `history`까지만 책임진다.
- `srb`는 D13을 받지 못하면 `null`이다. 엔진은 `null`을 "SRB 판단 불가"로 처리한다(12.3). `active`는 최근 3시간 안에 제목에 "Radio Emission/Burst"가 있는 경보가 있었는지이고, `events`는 최근 24시간 전파 경보 목록이다.
- `series`는 탭1 미니 그래프용이다. X선은 장파(0.1~0.8nm) 10분 간격 24시간, Kp는 NOAA 관측 3시간 간격 약 7일이다.
- `korea.sunSource`는 `kasi`(천문연 D7) 또는 `builtin`(내장 계산)이다.
- `sources[]`는 실패 시 `error`(원인)를, 의도적으로 건너뛴 경우 `note`를 추가로 가진다.
- 시각 문자열은 초 단위까지(밀리초 없음)로 통일한다.

- `sources[].ok`가 false이면 화면에 "일부 데이터 지연"을 표시하고 마지막 정상값을 쓴다.
- 한반도 기준 좌표는 대전(위도 36.35, 경도 127.38) 기본값으로 두고 변경 가능하게 한다.

**시간 규칙**: 저장·계산·API 응답은 모두 UTC(ISO 8601, `Z`)로 다루고, 화면 표시만 KST(UTC+9)로 바꿔 "KST"를 함께 적는다. NOAA 3일 예보의 날짜는 UTC 일자이므로 KST로는 당일 09:00~익일 09:00 구간임을 툴팁으로 안내한다. 주·야간은 해당 시각을 KST로 바꾼 뒤 일출·일몰과 비교한다. 혼동을 막기 위해 시각 필드명에는 `Utc` 또는 `Kst`를 붙인다.

### 3.3 재현 데이터

- 대상: 2024년 5월 9~13일(G5 폭풍).
- 결과물은 3시간 간격 `SwxState` 배열 하나(`data/replay-2024-05.json`, 2024-05-09 03:00~05-14 00:00 UTC, 40프레임)로 저장하고 배포물에 포함한다. `mode`는 `replay`.
- 각 프레임(기준 시각 T)은 **T까지 알 수 있었던 값만** 쓴다(미래 정보 금지).

| 항목 | 원천 | 산출 |
| --- | --- | --- |
| R | GOES-16 XRS-B 1분 평균(NOAA NCEI) | T 직전 3시간 최대 플럭스 → NOAA R척도 |
| S | GOES-18 SGPS 5분 평균(NCEI), 차등 채널을 ≥10 MeV로 적분 | T 직전 3시간 최대 → S척도. pfu는 근사값(운영값과 최대 약 3배 차이), S 등급은 SGAS 공식 기록(S1 개시 05-10 13:05 UTC, S2 정점 05-10 15:15·05-11 09:10 UTC)과 일치 확인 |
| G | GFZ 확정 Kp(D8) | T 직전 3시간 구간 Kp → G척도 |
| 예보·kpForecast | SWPC 3일 예보 당시 발표본(00:30·12:30 UTC, NCEI 보관) | T 이전 최신 발표본 |
| SRB | SWPC 사건 목록의 1415 MHz 전파폭발(RBR) | T 직전 3시간 안에 있으면 진행 중 |
| history | GFZ Kp·SN·F10.7 | T 이전 자료만 |

- 생성: `python -P scripts/extract_goes.py`(netCDF → 중간 JSON) → `node scripts/make-replay.mjs`. 원본은 `data-raw/`(git 제외)에 보관한다.

### 3.4 장차 전망 모델 학습 데이터

| ID | 데이터 | 엔드포인트 | 용도 |
| --- | --- | --- | --- |
| D10 | Kp 장기 이력(1932년~) | `https://kp.gfz.de/app/json/?start=...&end=...&index=Kp` | 학습·검증 |
| D11 | 태양흑점수(SN), F10.7(Fobs) | 같은 API, `index=SN` / `index=Fobs` | 태양활동 수준 변수 |
| D12 | NOAA 27일 전망 | NOAA SWPC 27-day outlook 텍스트 산출물(P0에서 주소 확인) | 비교 기준선 |

- 학습은 교육 전 P0에서 Python으로 끝내고, 배포물에는 학습된 계수 파일(`config/forecast-model.json`)만 넣는다.
- 실시간 전망에는 최근 60일 Kp·SN·F10.7만 필요하다. `/api/swx`가 D10·D11에서 함께 받아 `SwxState.history`로 넘긴다. GFZ 호출이 실패하면 D2(최근 약 7일)로 채울 수 있는 만큼 채우고 `sources`에 표시하며, 입력이 모자란 날짜는 기후학 기준선으로 표시한다.
- D12(NOAA 27일 전망)는 P0에서 확보되면 비교 기준선으로 쓰고, 못 구하면 "NOAA 비교 미완"으로 보고서에 적는다. 교육 트랙의 필수 항목이 아니다.

### 3.5 오프라인 대비 데이터

- `scripts/make-fallback.mjs`가 `/api/swx`의 정상 응답을 `data/fallback-latest.json`으로 저장한다. 발표 전날 밤과 당일 아침에 실행해 커밋·배포한다.
- 화면의 데이터 우선순위: `/api/swx` → 실패 또는 10초 초과 시 자동으로 `fallback-latest.json`(`mode: "fallback"`, 기준 시각을 크게 표시) → 사용자가 재현 모드 선택. 6.1의 "재현 모드로 보기" 버튼은 fallback 전환과 동시에 노출한다.
- 화면은 5분마다 자동 새로고침한다. `/api/swx`는 로그인 사용자별 응답이므로 CDN 공용 캐시를 쓰지 않고(`private, no-store`), 함수 메모리에 5분간 보관해 원천 호출을 줄인다(P1.5).
- `fallback-latest.json`은 정적 파일이라 로그인 없이도 주소를 알면 받을 수 있다. 공개 데이터라 교육 트랙에서는 허용하고, P9에서 배포물에서 제거한다(11.10).

## 4. 아키텍처와 기술 스택

빌드 도구 없는 정적 화면 + Vercel 서버 함수 1개 + 규칙 설정 파일의 최소 구성으로 간다. 판단 엔진은 브라우저에서 돌아 실시간과 재현 모드가 같은 코드를 쓴다.

**데이터 흐름**: 원천 API(D1~D7, D10·D11, D13) → `/api/swx`(수집·변환·5분 캐시) → 화면이 `SwxState` 수신 → `forecast.js`가 `forecast-model.json`으로 `outlook` 계산 → `engine.js`가 `rules.json`으로 판단 → 탭별 렌더링. 재현 모드는 `/api/swx` 대신 `replay-2024-05.json`을 읽고, 이후 단계는 같다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 화면 | HTML·CSS·순수 JS(ES 모듈) | 빌드 오류 없음, 교육 중 디버깅 최소 |

## 5. 판단 엔진 명세

엔진은 `evaluate(state, rules, options = {})` 순수 함수 하나다. 입력은 `SwxState`와 `rules.json`, 화면 토글(`options.lowAltitudeOps`, 12.3)이고, 출력은 체계별 단계·근거·권고다. 단계는 확정된 기준대로 **I 관찰(1~2등급) · II 대비(3등급) · III 조치(4~5등급)**, 해당 없으면 정상이다. 모든 규칙에는 출처 태그(`source`)를 두고 근거 표시에 함께 낸다.

### 5.1 rules.json 구조(발췌)

```json
{
  "version": "0.1",
  "levels": ["정상", "I 관찰", "II 대비", "III 조치"],
  "scaleToLevel": { "0": 0, "1": 1, "2": 1, "3": 2, "4": 3, "5": 3 },
  "systems": [
    {
      "id": "hf_day",
      "name": "주간 HF망",
      "drivers": [ { "scale": "R", "when": "korea.isDaytime" } ],
      "messages": {
        "2": "HF 수십분~1시간 두절 가능. 위성망 우선 운용",
        "3": "낮 반구 HF 수시간 두절. HF를 예비수단에서 제외"
      },
      "pace": { "P": "위성통신", "A": "유선망", "C": "VHF 중계", "E": "전령" }
    },
    {
      "id": "gnss",
      "name": "GNSS 항법·정밀유도",
      "drivers": [ { "scale": "G" } ],
      "messages": { "2": "GNSS 오차 증가. 관성항법 병행 준비", "3": "정밀항법 신뢰 불가. 관성항법 병행" }
    }
  ]
}
```

- 한 체계에 원인이 여럿이면(예: UHF 위성통신 = G, S) **가장 높은 단계**를 채택하고 근거에 모두 표시한다.
- `when` 조건이 거짓이면(예: R 발생인데 야간) 단계는 정상, 근거는 "한반도 야간으로 직접 영향 없음"으로 남긴다.
- 체계 목록은 부록 A의 9개 체계를 그대로 옮긴다. PACE 항목은 일반적 예시이며 부대별로 바꿔 쓸 수 있게 한다.

### 5.2 출력 형식

```json
{
  "overall": 2,
  "headline": "향후 24시간 주간 HF 제한 가능, 위성망 우선 운용 권고",
  "systems": [ { "id": "hf_day", "level": 2, "reasons": ["R3 (X1.4) · 한반도 주간"], "message": "..." } ],
  "horizon": { "now": 2, "h6": 2, "h24": 1, "d3": 2, "d4_27": 1 }
}
```

`horizon.d4_27`은 5.5의 4~27일 전망 칸 결과이며 최대 1(I 관찰)이다.

### 5.3 필수 테스트 케이스

| # | 입력 | 기대 결과 |
| --- | --- | --- |
| T1 | 모든 등급 0 | 전 체계 정상 |
| T2 | R3, 주간 | 주간 HF망 II 대비 |
| T3 | R3, 야간 | 주간 HF망 정상 + 야간 근거 문구 |
| T4 | G3 | GNSS·시각동기·UHF 위성 II 대비 |
| T5 | G5 + S2 | GNSS III 조치, UHF 위성은 G5·S2 중 높은 단계(III) 채택, 근거에 둘 다 표시 |
| T6 | 일부 데이터 누락(`ok:false`) | 오류 없이 판단, 누락 안내 포함 |
| T7 | 2024년 5월 재현 최대치 시점 | 종합 III 조치 |

### 5.4 AI 장차 전망 모델(Must)

시간 범위마다 판단 근거를 달리한다. **현행작전은 예보, 장차작전은 확률 전망, 장기 계획은 기저확률**로 제공하며, 예측 가능 범위는 모델이 아니라 태양의 물리적 특성이 정한다.

| 시간 범위 | 근거 | 제공 형태 | 작전 활용 |
| --- | --- | --- | --- |
| 0~3일 | CME 관측 기반 NOAA 예보 | 등급 예보(5.1~5.3 규칙) | 현행작전, PACE 전환 |
| 4~27일 | 태양 자전주기(약 27일) 재귀성 | 일자별 G1·G3 이상 확률 | 장차작전 기획 |
| 27일 이상 | 태양주기 위상, 계절(분점 무렵 활동 증가) | 기저확률 | 장기 작전·전력운용 계획 |

**모델 명세**

- 예측 대상: 기준일로부터 D+1~D+27 각 날짜의 일 최대 Kp가 5 이상(G1+), 7 이상(G3+)일 확률. 목표별 모델 1개씩 총 2개.
- 입력 변수: 대상일 27일 전·54일 전 일 최대 Kp, 기준일 최근 3일 최대 Kp, 예측 거리(h), 최근 27일 평균 SN·F10.7, 계절(연중 날짜의 sin·cos).
- 알고리즘: 로지스틱 회귀. 계수를 JSON으로 내보내 브라우저에서 계산할 수 있고, 가중치로 근거를 설명할 수 있다. 시간이 남으면 경사부스팅과 비교만 한다.
- 학습·검증: 1996~2019년 학습, 2020년~현재 검증(25주기 전체를 보지 못한 상태로 평가).
- 기준선: ① 기후학(해당 월의 과거 평균 발생률), ② 27일 재귀(27일 전 상태에 따른 조건부 발생률). ③ NOAA 27일 전망은 아카이브를 확보했을 때만 추가한다(12.4).
- 평가 지표: Brier skill score(기준선 대비 개선도), 신뢰도 곡선(예측 확률과 실제 발생률의 일치).
- 채택 규칙: 검증 기간에 ②보다 나으면 ML, 아니면 ②를 전망으로 표시한다. 어느 쪽이든 화면에 근거(`basis`)와 성능을 공개한다.
- R(플레어): 장기 예측을 하지 않는다. 현재 SN 수준에 따른 일 R3+ 기저확률만 NOAA 척도 빈도로 근사해 표시한다.

**불균형·보고 방식**: G3+는 전체 일수 중 수 % 수준의 드문 사건이므로 정확도는 쓰지 않고 BSS와 신뢰도 곡선만 쓴다. **클래스 가중치는 쓰지 않는다**. 그래야 로지스틱 회귀의 출력이 그대로 확률이 되어 보정 단계 없이 브라우저에서 계수만으로 계산할 수 있다. 신뢰도 곡선이 크게 어긋날 때만 Platt 보정 계수 2개(a, b)를 `forecast-model.json`에 추가한다. 성능은 예측 거리 h=1~3, 4~13, 14~27일 구간별로 따로 보고하고, 화면 배지에도 구간별 BSS를 표시한다. 채택 규칙은 구간별로 적용해, ML이 기준선을 못 이기는 구간은 27일 재귀로 표시한다. 27일 재귀 조건부 발생률표도 `forecast-model.json`에 함께 넣어 브라우저가 기준선을 직접 계산하게 한다.

**출력 형식**: 3.2 `SwxState`의 `outlook`·`outlookSkill`·`rBaseline`을 그대로 쓴다(날짜 필드는 `dateUtc`, 구간별 성능은 `outlookSkill.byHorizon`). 숫자는 형식 예시이며 실제 성능은 P0 학습 후 확정한다.

**교육 트랙 범위**: 12.4의 확장 평가(위상별 BSS, 부트스트랩, 추가 변수, 롤링 홀드아웃)는 고도화(P10)로 미룬다. 단, 12.4의 **사용자 고지 문구**는 교육 트랙에서도 필수다.

**추가 테스트**: T8 outlook이 27개이고 확률이 0~1 범위이며 basis가 있다. T9 동일 입력에서 Python 학습 결과와 JS 계산 결과가 소수점 셋째 자리까지 같다.

### 5.5 미래 칸·종합 단계 산정 규칙

매트릭스의 각 시간 칸은 아래 규칙으로 등급을 만든 뒤 5.1의 `scaleToLevel`로 단계를 정한다. 확률 임계값은 모두 `rules.json`의 `horizonRules`에 두며, 아래 숫자는 기본값이다.

| 칸 | G | R | S |
| --- | --- | --- | --- |
| 현재 | `scales.G` | `scales.R`(한반도 주간일 때만) | `scales.S` |
| 6시간·24시간 | 해당 구간 `kpForecast` 최대 Kp를 G등급으로 변환 | 구간이 걸친 UTC 일자의 `R35pct` ≥ 30%이면 R3, `R12pct` ≥ 50%이면 R1(구간 안에 한반도 주간이 있을 때만) | `S1pct` ≥ 50%이면 S1 |
| 3일 | `forecast[].Gmax`의 일별 최대 | 같은 확률 규칙, 일별 최대 | 같은 확률 규칙 |
| 4~27일 전망 | 기간 중 최대 `pG3` ≥ 15% 또는 `pG1` ≥ 50%이면 I 관찰 | 예측하지 않음(기저확률만 별도 표시) | 예측하지 않음 |

- NOAA는 S1 확률만 주므로 미래 칸의 S는 I 관찰이 상한이다.
- 4~27일 칸은 확률 전망이므로 I 관찰을 상한으로 둔다.
- 확률에서 나온 칸은 점선 테두리로 표시해 관측 기반 칸과 구분한다.

**종합 단계(overall)**: 현재 열에서 체계별 단계의 최댓값이다. 한 줄 판단(headline)은 최고 단계 체계의 문구를 쓰고, 동률이면 `rules.json`의 체계 순서(우선순위)를 따른다. 모두 정상이면 미래 열 중 가장 가까운 I 관찰 이상 칸을 안내한다(예: "현재 영향 없음, D+2 GNSS I 관찰 예상").

**추가 테스트**: T10 6시간 칸에서 R35pct 40%이고 해당 구간이 전부 야간이면 주간 HF망 정상. T11 두 체계가 같은 최고 단계일 때 headline이 우선순위 체계를 따른다.

### 6.1 상태 처리

- **로딩**: 카드 자리에 회색 틀 표시, 10초 넘으면 "재현 모드로 보기" 버튼 노출.
- **오류**: 원천별 상태 점(초록/빨강), 마지막 정상 시각 표시. 화면은 멈추지 않는다.
- **빈 결과(전부 정상)**: "현재 영향 없음" + "대형 사례 재현 보기" 안내. 발표 당일 조용한 상황에 대비한다.
- **출처 표기**: 하단에 NOAA SWPC, GFZ(CC BY 4.0), 한국천문연구원, "공개 데이터 기반 시제품" 문구.

### 6.2 디자인 기준

- 색상은 단계 4개만 의미를 갖는다: 정상(초록) · I 관찰(노랑) · II 대비(주황) · III 조치(빨강). 그 외는 무채색.

### 6.3 탭6 AI 장차 전망(Must)

- 27일 달력: 일자별 G1+ 확률을 색 농도로, G3+ 확률을 숫자로 표시한다.
- 작전 기간 선택: 시작일과 종료일을 고르면 "기간 중 G3+ 1회 이상 확률"을 1 − ∏(1 − p)로 계산해 보여준다.
- 상단 배지: 근거(ML 또는 27일 재귀)와 기준선 대비 성능을 항상 표시한다.
- 하단 고지: "확률 전망이며 확정 예보가 아님. 코로나 구멍에서 오는 반복형 폭풍에만 예측력이 있고, 코로나물질방출(CME)로 생기는 폭풍은 사실상 예측할 수 없음. 플레어(R)는 장기 예측 불가로 기저확률만 제공."
- 영향 매트릭스(탭2)에도 "4~27일 전망" 열을 추가해, 5.5의 임계치를 넘으면 G 관련 체계를 I 관찰(점선 칸)로 표시한다. 임계치는 rules.json의 `horizonRules`에 둔다.
- 재현 모드에서도 `history`가 있으면 같은 계산으로 전망을 보여준다(선택).

### 6.4 용어 도움말(Should)

- 비전문가 심사위원을 위해 주요 용어 옆에 (i) 표시를 두고, 누르면 2문장 이내 설명을 보여준다.

**운용 팁**

- 페이즈마다 새 대화를 시작하고 `/pickup`으로 맥락을 불러온다. 대화가 길어질수록 앞의 규칙을 놓치기 쉽다.
- 큰 작업은 계획 모드로 먼저 계획만 받고, 확인한 뒤 실행한다.
- 화면 문제는 "어느 탭, 무엇이, 어떻게 다른가"로 말하고 가능하면 스크린샷을 함께 붙인다.
- 막히면 20분 이상 붙잡지 말고 직전 태그로 되돌린 뒤 범위를 줄여 다시 요청한다.

## 9. 계정 전환 대비 작업 인계 체계

Pro 계정 2개를 번갈아 쓸 수 있도록, **작업 상태는 대화가 아니라 저장소의 문서와 Git에 남긴다**. 계정 A의 사용량이 바닥나면 같은 VS Code 터미널에서 계정 B로 다시 로그인하고, 문서를 읽혀 바로 이어간다.

### 9.1 개발 문서 4종

문서가 많으면 갱신이 빠진다. 그래서 인계·진행·결정 기록을 `CURRENT_STATUS.md` 하나로 합쳐 문서를 4개로 고정한다. 세부 변경 기록은 Git 커밋 이력이 맡는다.

| 파일 | 역할 | 갱신 방식 |
| --- | --- | --- |
| `CLAUDE.md` | Claude Code 작업 규칙(무엇을 어떻게 만들 것인가) | 규칙이 바뀔 때만 |
| `README.md` | 사람용 소개: 목적, 구조, 실행·배포 방법, 출처 | 실행 방법·구조가 바뀔 때 |
| `docs/PRD.md` | 요구사항(무엇을 만들 것인가) | 범위 변경 시만, 부록 C에 이력 추가 |
| `docs/CURRENT_STATUS.md` | 현재 페이즈, 페이즈 체크리스트, 진행 중 작업, 다음 할 일, 알려진 문제, 결정 로그 | 기능 하나 끝날 때마다. 결정 로그는 끝에 추가만 |
| Git 커밋 이력 | 세부 변경 기록 | 기능 단위로 자주 커밋 |

### 9.2 CURRENT_STATUS.md 형식

저장소의 `docs/CURRENT_STATUS.md`가 형식의 기준이다. 섹션은 아래 순서로 고정한다.

1. 헤더: 마지막 갱신 시각(KST)·계정
2. 지금 상태: 현재 페이즈, 마지막으로 완료한 것(커밋 해시), 진행 중이던 것(파일명과 진척 위치)
3. 다음 할 일(순서대로)
4. 알려진 문제·주의사항
5. 확인 방법
6. 페이즈 체크리스트(P0~P6)
7. 결정 로그(`날짜 | 결정 | 이유`, 끝에 추가만)

### 9.3 자동화 명령어(사용자 정의 슬래시 명령)

저장소의 `.claude/commands/` 폴더에 두 파일을 두면, 어느 계정에서든 `/handoff`, `/pickup`으로 쓸 수 있다. 파일이 저장소에 있으므로 계정과 무관하다.

`.claude/commands/handoff.md`

```markdown
현재 작업 상태를 인계 문서로 정리해줘. 코드는 더 수정하지 마.
1. docs/CURRENT_STATUS.md의 헤더·지금 상태·다음 할 일·알려진 문제·확인 방법을 덮어써. 미완료 작업은 파일명과 어디까지 했는지 구체적으로.
2. 같은 파일의 페이즈 체크리스트에서 완료 항목을 체크해.
3. 이번 세션에서 내린 결정이 있으면 결정 로그 끝에 "날짜 | 결정 | 이유"로 추가해(기존 행은 수정 금지).
4. 모든 변경(미완성 코드 포함)을 "[HANDOFF] 요약" 메시지로 커밋하고 push해.
5. 끝나면 커밋 해시와 다음 할 일 1줄만 보여줘.
```

`.claude/commands/pickup.md`

```markdown
다른 계정이나 이전 세션에서 하던 작업을 이어받는다. 코드를 수정하기 전에:
1. CLAUDE.md와 docs/CURRENT_STATUS.md를 읽어. PRD는 현재 페이즈와 관련된 장만 읽어.
2. git log --oneline -10, git status, git diff로 실제 상태를 확인해.
3. CURRENT_STATUS 내용과 실제 코드가 다르면 그 차이를 먼저 보고해.
4. 현재 페이즈, 다음 작업 1개, 확인 방법을 5줄 이내로 요약하고 내 승인을 기다려.
```

### 9.4 계정 전환 절차(VS Code 터미널)

1. 계정 A에서 사용량 경고가 보이면 새 기능을 시작하지 말고 `/handoff` 실행
2. 커밋·push 확인 후 `/logout`
3. `/login`으로 계정 B 로그인(또는 종료 후 `claude` 재실행)
4. `/model`에서 Opus 5.5 확인
5. `/pickup` 실행 → 요약 확인 후 승인

**`/handoff` 없이 갑자기 끊겼을 때**: 파일은 로컬에 그대로 남아 있다. 계정 B에서 `/pickup`을 실행하면 `git diff`로 미커밋 변경을 찾아 이어간다. 그래서 평소에도 기능 하나마다 커밋하는 것이 중요하다.

### 9.5 운영 원칙

- 상태의 기준은 항상 문서와 Git이다. 이전 대화 기록에 의존하지 않는다.
- 기능 하나를 끝낼 때마다 CURRENT_STATUS.md를 갱신한다. 한도 직전에 몰아서 쓰면 갱신 자체가 끊길 수 있다.
- 페이즈 완료 시에는 어느 계정이든 `/handoff` 후 태그(`p3-done` 등)를 단다.
- Pro 사용량은 claude.ai 채팅과 Claude Code가 함께 쓴다. 교육 중 채팅은 계정 B, 개발은 계정 A처럼 용도를 나눠두면 전환 횟수가 줄어든다.
- 긴 대화는 사용량을 빨리 소모한다. 페이즈마다 새 대화를 시작하고 `/pickup`으로 맥락을 불러온다.

## 11. 고도화 트랙: 실사용 수준 체계(교육 이후)

고도화 목표는 인터넷 환경에서 실제 운용 가능한 서비스(L2)다. 국방망 탑재는 목표가 아니며, 공개 데이터만으로 24시간 무중단 운영되고 승인된 사용자가 역할에 따라 업무에 활용할 수 있는 수준을 완성 기준으로 삼는다. 백엔드는 Supabase(Postgres·Auth)를 쓴다. 주 6~8시간 개발 기준 약 13~15주를 예상하며, 전 과정을 바이브코딩으로 수행할 수 있다.

### 11.1 목표 수준

| 수준 | 상태 | 달성 수단 |
| --- | --- | --- |
| L1 시연 | 공개 데이터 실시간·재현, 배포 URL | 교육 트랙(P0~P6) |
| L2 실운용(목표) | 24시간 자동 수집·이력 축적, 알림, 예측 성과 추적, 규칙 편집·권한, 백업·모니터링·장애 대응, 운영 매뉴얼 | 바이브코딩(P7~P13) |
| 참고: 국방망 탑재 | 목표 아님. 데이터 입구가 하나라 구조상 확장 여지만 남긴다 | 해당 없음 |

### 11.2 바이브코딩으로 되는 것과 사람·조직이 해야 하는 것

| 영역 | 바이브코딩으로 가능 | 사람이 해야 하는 것 |
| --- | --- | --- |
| 기능 개발 | 거의 전부 | 요구사항 결정, 결과 확인 |
| 품질 | 테스트·CI·정적 분석 자동화 | 테스트 시나리오 승인, 리뷰 |
| 보안 | 인증·권한, 보안 헤더, 요청 제한, 보안약점·의존성 자동 점검 | 공개 범위 결정, 부대 대외 게시 규정 확인 |
| 과학적 타당성 | 백테스트 코드, 평가 리포트 | 임계값 전문가 검토(우주기상 기관·천문연) |
| 운영 | 모니터링·백업 자동화, 운영 매뉴얼, 장애 대응 절차서 | 운영자 역할, 사용자 모집·피드백 |

바이브코딩의 가장 큰 위험은 **개발자가 이해하지 못한 코드가 쌓여 유지보수가 불가능해지는 것**이다. 그래서 고도화 트랙은 테스트 우선, 모듈 설명 문서, 사람 검토 후 병합을 규칙으로 둔다(11.7).

### 11.3 고도화 아키텍처

- **수집과 화면 분리**: 예약 작업(Supabase pg_cron이 15분마다 Edge Function 호출, 11.10)이 수집·검증 후 DB에 저장하고, 화면은 DB의 최신값을 읽는다. 원천 API가 장애여도 화면은 영향을 받지 않는다.
- **DB**: 관리형 Postgres(예: Supabase). 일일 백업과 복구 절차를 두고, 저장 용량은 11.10의 보존 정책을 따른다.
- **원천 이중화**: 원천별 어댑터를 두고, NOAA Kp가 장애면 GFZ Kp로 전환하는 등 대체 출처를 지정한다. 어댑터는 모두 `SwxState`를 낸다.
- **검증**: `SwxState`와 `rules.json`을 JSON Schema로 검증하고, 실패한 데이터는 저장하지 않고 경고한다.
- **인증·보안**: Supabase Auth 로그인과 역할별 권한(11.9). 열람은 승인된 로그인 사용자만 허용하는 것을 기본으로 한다. 보안 헤더(CSP 등), API 요청 제한을 적용한다.
- **코드 품질**: 엔진·전망·어댑터는 TypeScript로 전환해 타입으로 오류를 막는다. 화면은 필요할 때 점진 전환한다.
- **감사·모니터링**: 규칙 변경 이력(누가·언제·무엇을·왜), 수집 실패율·데이터 지연·오류 로그, 외부 가용성 점검. 수집이 연속 실패하면 운영자에게 알린다.

### 11.9 인증·권한·관리자 모드(Supabase)

Supabase Auth로 로그인하고, 승인된 사용자만 역할에 따라 기능을 쓴다. 권한은 화면이 아니라 **DB의 행 단위 보안(RLS)에서 강제**해, 화면 코드가 우회돼도 데이터가 보호되게 한다.

#### 역할과 권한

| 기능 | 열람자(viewer) | 운용자(operator) | 관리자(admin) |
| --- | --- | --- | --- |
| 대시보드·이력·장차 전망 열람 | O | O | O |
| 알림 구독, 피드백 작성 | O | O | O |
| 일일 브리핑 생성·내려받기 | - | O | O |
| 백테스트 실행 | - | O | O |
| 규칙 변경 초안 작성 | - | O | O |
| 규칙 변경 승인·활성화·롤백 | - | - | O |
| 가입 승인, 역할 변경, 계정 정지 | - | - | O |
| 시스템 설정·수집 현황·감사 로그 열람 | - | - | O |

규칙 변경은 운용자가 초안을 올리고 관리자가 승인하는 **2인 확인** 구조다. 작성자와 승인자는 반드시 달라야 하며 DB 함수에서 강제한다. 활성 관리자가 1명뿐인 비상시에만 사유를 입력하고 본인 승인을 허용하며, 감사 로그에 "비상 본인 승인"으로 남긴다.

#### 가입·승인 흐름

1. 사용자가 이메일·비밀번호로 가입 신청(이메일 인증 필수). 수집 정보는 이메일, 표시 이름, 소속 구분(군·공공기관·연구기관·기타)만 받고 부대명은 받지 않는다.
2. 가입 직후 상태는 `pending`(승인 대기). 아무 데이터도 볼 수 없고 "승인 대기 중" 화면만 보인다.
3. 관리자에게 새 가입 알림이 가고, 관리자가 역할을 정해 승인하면 `active`.
4. 정지된 계정(`suspended`)은 로그인은 되지만 데이터 접근이 막힌다.
5. 90일 미접속 계정은 관리자 화면에 휴면 후보로 표시한다(자동 정지는 하지 않음).

#### 관리자 계정 운영 원칙

- **최초 관리자**: Supabase 대시보드의 SQL로 1회만 지정한다(부트스트랩). 이후 역할 변경은 모두 관리자 모드에서만 한다.
- **관리자 전용 계정 분리**: 일상 열람용 계정과 관리자 계정을 나눈다.
- **관리자 2단계 인증(MFA) 필수**: Supabase Auth의 TOTP(인증 앱)를 쓰고, 관리자 기능은 2단계 인증을 거친 세션(aal2)에서만 동작한다.
- **관리자 최소 2명**: 본인 외 부관리자 1명을 두어 잠김 사고에 대비한다. 마지막 활성 관리자는 강등·정지할 수 없도록 DB 함수에서 막는다.
- **비상 접근**: 모든 관리자가 잠기면 Supabase 프로젝트 소유자 계정으로 복구한다. Supabase·Vercel·GitHub 소유자 계정에도 2단계 인증을 켜둔다.
- **감사 로그**: 가입 승인, 역할 변경, 정지, 규칙 승인·롤백, 설정 변경을 모두 기록한다. 감사 로그는 수정·삭제할 수 없다.

#### 데이터 모델

| 테이블 | 내용 | 접근(RLS) |
| --- | --- | --- |
| `profiles` | 표시 이름, 소속 구분, 역할, 상태, 승인자·승인 시각 | 본인 조회, 관리자 전체 조회. 역할·상태 변경은 관리자 함수로만 |
| `swx_snapshots` | 15분 수집 `SwxState` | 활성 사용자 조회, 쓰기는 수집기(서버)만 |
| `rule_versions` | rules.json 버전, 작성자, 상태(초안·승인·활성·폐기), 사유 | 활성본 전체 조회, 초안은 운용자 이상, 승인은 관리자 |
| `alert_subscriptions` | 채널, 최소 단계, 관심 체계 | 본인만 |
| `feedback` | 유용 여부, 짧은 의견 | 본인 작성·조회, 관리자 전체 조회 |
| `audit_logs` | 행위자, 행위, 대상, 변경 전후, 시각 | 관리자 조회만, 수정·삭제 불가 |

```sql
-- 핵심 구조 스케치(실제 마이그레이션은 Claude Code가 작성)
create type app_role as enum ('viewer', 'operator', 'admin');      -- 선언 순서 = 권한 순서
create type account_status as enum ('pending', 'active', 'suspended');

create table public.profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text not null,
  org_type text check (org_type in ('군', '공공기관', '연구기관', '기타')),
  role app_role not null default 'viewer',
  status account_status not null default 'pending',
  approved_by uuid references auth.users,
  approved_at timestamptz,
  created_at timestamptz not null default now()
);

-- 현재 사용자가 활성 상태이고 최소 역할 이상인지
create function public.has_role(min_role app_role) returns boolean
language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from profiles p
    where p.id = auth.uid() and p.status = 'active' and p.role >= min_role
  );
$$;

alter table profiles enable row level security;
create policy profiles_self on profiles for select using (id = auth.uid());
create policy profiles_admin on profiles for select using (has_role('admin'));
-- update 정책은 두지 않는다. 역할·상태 변경은 admin_set_role() 함수로만:
--   ① 호출자 has_role('admin') 그리고 2단계 인증 세션(aal2)
--   ② 마지막 활성 관리자 강등·정지 금지
--   ③ audit_logs에 변경 전후 기록
```

- 가입 시 `auth.users` 트리거로 `profiles`를 `pending` 상태로 자동 생성한다.
- 모든 테이블은 RLS를 켜고 기본 거부에서 필요한 정책만 연다.
- 화면은 공개 키(anon key)만 쓴다. 관리자 키(service_role)는 Vercel 서버 함수(수집기, 알림 발송)에서만 쓰고 화면에 노출하지 않는다.
- 서버 함수는 요청의 로그인 토큰을 검증하고 역할을 다시 확인한다.
- 스키마 변경은 Supabase CLI의 `supabase/migrations/`로만 한다. 대시보드에서 직접 고치지 않는다.

#### 관리자 모드 화면(`/admin`)

| 탭 | 기능 |
| --- | --- |
| 사용자 | 승인 대기 목록, 승인·거절, 역할 변경, 정지·복구, 휴면 후보 |
| 규칙 | 버전 목록, 초안 비교(변경 전후), 과거 사례 적용 미리보기, 승인·활성화·롤백 |
| 알림 | 발송 이력, 채널 상태, 테스트 발송 |
| 시스템 | 수집 성공률·지연, 원천별 상태, 마지막 백업 시각 |
| 감사 로그 | 기간·행위자·행위 필터, 내보내기(CSV) |
| 피드백 | 유용도 통계, 의견 목록 |

관리자 모드는 화면 상단에 눈에 띄는 색 띠로 구분하고, 2단계 인증이 없는 세션이면 진입 전에 인증 코드를 요구한다.

- 수집기·화면·백테스트는 모두 같은 엔진 코드와 지정된 규칙 버전으로 판정한다.

## 12. 근거 기반 보강(v2)

문헌·공식 자료 조사(부록 B) 결과를 반영한 결정이다. v2.1에서 이 장의 내용을 1~7장 본문에 반영했으므로 앞 장과 충돌하지 않는다. 각 항목의 적용 시점은 12.8을 따른다. 핵심은 세 가지다. 단계 명칭을 국가 위기경보와 분리하고, R·S·G 외의 영향 동인(태양전파폭발·지역 전리층)을 다루며, 낮은 등급에서도 영향이 생기는 예외를 규칙에 넣는다.

### 12.1 단계 명칭 변경과 국가 체계 대응

기존 "주의·경계·심각"은 국가 우주전파재난 위기경보(관심·주의·경계·심각)와 이름이 같지만 발령 기준이 다르다. 회의에서 혼선이 생기지 않도록 **작전영향 등급 I 관찰 · II 대비 · III 조치**로 바꾼다(본문 전체 반영 완료).

| SWx-C2 작전영향 등급 | NOAA 척도 | 우주환경센터 우주전파환경 경보 | 국가 우주전파재난 위기경보 |
| --- | --- | --- | --- |
| 정상 | 0 | - | - |
| I 관찰 | 1~2 | 1~2단계 | - |
| II 대비(작전 조치 기준선) | 3 | 3단계 | - (국가 기준보다 한 단계 앞선 작전 대비) |
| III 조치 | 4~5 | 4~5단계 | 4단계 발생 시 관심, 5단계 발생 시 주의 등(지속·피해에 따라 상향) |

- 화면 상단에는 ① NOAA R/S/G ② 우주환경센터 경보 단계 ③ 국가 위기경보 상태 ④ SWx-C2 작전영향 등급을 나란히 표시한다. ②·③는 데이터를 확보하지 못하면 "미연동"으로 표기한다.
- 작전 조치 기준선(3등급)은 유지한다. 근거는 NOAA 등급 영향 서술(R3 광역 HF 두절, S3 위성 SEU, G3 저궤도 항력·HF 간헐 장애)과 R3 한 번으로 극항로 항공편이 우회한 2003년 사례다.

### 12.2 추가 영향 동인과 데이터

X선 등급(R)만으로는 GNSS·레이더 간섭을 판단할 수 없다. 2006년 12월 5일은 X선 기준 가장 강한 플레어였지만 GPS를 약화시키지 않았고, 12월 6일 태양전파폭발은 태양활동 극소기였는데도 낮 반구 GPS 수신기 절반 이상을 비정상으로 만들었다. 또 Kp 기반 G척도는 전지구 3시간 평균이라 한반도 전리층 영향을 직접 나타내지 않는다(2024년 5월 한반도 TEC 최대 70% 감소, 야간 강한 신틸레이션).

| 동인 | 입력 데이터 | 적용 체계 | 적용 시점 |
| --- | --- | --- | --- |
| 태양전파폭발(SRB) | NOAA SWPC 경보·주의보 목록(전파폭발 항목). 엔드포인트·경보 정의는 P0에서 확인 | GNSS·레이더·L밴드 위성통신 | 교육 트랙(P2) |

### 12.3 판단 규칙 보강

1. **출처 태그**: rules.json의 모든 규칙에 `source` 필드를 두고(예: `NOAA-scales`, `ICAO-Doc10100`, `Lee2024`), 화면의 근거 표시에 출처를 함께 보여준다.
2. **SRB 규칙**: SWPC 전파폭발 경보가 있고 한반도가 주간이면 GNSS·레이더를 II 대비로 올린다. SRB 입력을 받지 못하면 GNSS 칸에 "SRB 판단 불가"를 표시하고, R등급만으로 GNSS 등급을 올리지 않는다.
3. **지역 보정(고도화)**: GNSS·UHF 위성통신 등급 = max(G 기반 등급, 지역 TEC·ROTI 기반 등급). 지역 자료가 없으면 G 기반으로 판정하되 "지역 미보정" 배지를 붙인다. 교육 트랙은 배지만 표시한다.
4. **저궤도 예외(G1 규칙)**: 화면에 "저고도 운용·발사 국면" 토글을 둔다. 켜져 있으면 저궤도 정찰위성(leo_isr)은 G1부터 II 대비다(2022년 2월 G1급 폭풍에 저궤도 위성 49기 중 38기 손실 근거).
5. **지속·반복 상향(고도화 P8, 이력 DB 필요)**: 국가 체계 방식을 따라, 같은 체계가 24시간 안에 II 대비를 2회 이상 받거나 II가 48시간 이상 이어지면 III 조치로 올린다.
6. **해제 규칙(고도화 P8, 이력 DB 필요)**: 등급을 낮출 때는 임계 미만이 일정 시간 이어져야 한다. 기본값은 R·S·SRB 45분(ICAO 방사선 권고 종료 규칙 차용), G 3시간(Kp 1구간)이며 rules.json의 `clearRules`에 둔다.
7. **보조 정량 지표(고도화)**: 자료를 확보하면 ICAO 방식의 영역별 임계값(수직 TEC 125 TECU, 폭풍 후 MUF 30% 저하, 방사선 30/80 μSv/h)을 보조 규칙으로 추가한다.
8. **시각동기**: GNSS 추적 상실 → holdover 진입 → 장비별 허용시간을 PACE 전환 신호로 쓴다. 허용시간은 공개 근거가 없으므로 값을 두지 않고, 점검 항목으로만 표시한다.

교육 트랙(P2)은 1·2·4번과 3번의 배지 표시만 구현한다. 5·6번은 판정 이력이 있어야 하므로, 단일 스냅샷만 받는 교육 트랙 엔진(순수 함수)에서는 구현하지 않고 고도화 P8(이력 DB)에서 추가한다.

추가 테스트(교육 트랙): T12 SRB 입력 없음(`srb: null`) → GNSS "SRB 판단 불가" 표시. T13 R3만 있고 SRB 없음 → GNSS 등급 미상향. T14 저고도 토글 ON + G1 → leo_isr II.
추가 테스트(고도화 P8): T15 24시간 내 II 2회 → III. T16 G 임계 미만 2시간 경과 → 등급 유지, 3시간 → 해제.

### 12.4 장차 전망 모델 보완

문헌상 2일을 넘는 선행 예측에서는 27일 재귀가 주된 정보원이고, 재귀 예보는 태양주기 하강기에 특히 유효하다. 현재 5.4 설계는 방향이 맞으며 아래를 추가한다. **교육 트랙에서는 마지막 "사용자 고지"만 필수**이고, 나머지는 P0에서 시간이 남으면 시도하되 기본은 고도화 P10에서 수행한다.

- **기준선 3개**: ① 기후학(태양주기 위상별) ② 27일 재귀 ③ NOAA 27일 전망(과거 전망 아카이브를 모아 재구성). ③ 아카이브를 P0에서 확보하지 못하면 ①②로 시작하고 "NOAA 비교 미완"을 보고서에 적는다. ③을 넘지 못하면 발표에서 "NOAA 대비 우수"를 주장하지 않는다.
- **추가 변수**: 1·2 태양자전 전 Kp·Ap, 27일 재귀 강도(최근 자전들 사이의 상관), F10.7, 태양주기 위상, 계절 항.
- **평가 방식**: 시간 순서를 지키는 롤링 홀드아웃, 태양주기 상승기·극대기·하강기별 BSS 분리 보고, 부트스트랩 신뢰구간, 신뢰도 곡선과 예측 분포(sharpness) 히스토그램. G3+는 발생일 비율이 약 3% 수준이라 신뢰도 구간 수를 줄여 평가한다.
- **사용자 고지**: "코로나 구멍에서 오는 반복형 폭풍에만 예측력이 있고, 코로나물질방출(CME)로 생기는 폭풍은 사실상 예측할 수 없다"를 탭6과 평가 보고서에 항상 표시한다.

### 12.6 역할 정립: 공식 예보와 경합하지 않는다

- 공군 우주작전전대 우주기상대는 자체 관측장비와 예·경보체계를 운용하고, 국가 공식 예·경보는 우주항공청 우주환경센터가 한다.
- SWx-C2는 **공개자료 기반 영향 번역·교육·기획 도구**다. 화면 하단에 "공식 예·경보가 있으면 공식 예·경보를 우선한다"를 고지한다.
- 발표와 협업 제안에서는 "공식 예보를 지휘통신 조치로 번역하는 계층"으로 설명한다. 이는 NATO 기술보고서가 지적한 "우주기상 모델이 작전 영향을 필요한 수준으로 제시하지 못한다"는 공백과 같은 맥락이다.

### 12.7 발표용 핵심 근거 5개

1. **1967년 레이더 재밍 오인 위기**: 태양전파폭발이 미 조기경보 레이더를 교란했고, 우주기상 판단이 적 재밍 오판을 막았다.
2. **2006년 태양활동 극소기의 GPS 장애**: 낮 반구 GPS 수신기 120대 이상 중 정상 동작이 60대 미만으로 줄었다. 태양이 조용한 시기에도 영향은 생긴다.
3. **2022년 G1급 폭풍에 저궤도 위성 38/49기 손실**: 등급이 낮다고 영향이 없는 것이 아니다.
4. **2024년 5월 한반도 상공 TEC 최대 70% 감소**: 한국천문연구원이 직접 관측한 우리 전구의 사례다.
5. **국제 추세와 국내 공백**: ICAO·NATO·미국 국가전략은 영향 기반·영역별 임계값 체계로 가고 있다. 국방부는 국가 표준매뉴얼상 국방 실무매뉴얼 주체지만, 지상군·전구 지휘통신 관점의 영향 번역 도구는 찾기 어렵다.

5번의 "국내 공백"은 이번 조사 범위에서 확인하지 못했다는 뜻이므로 "없다"고 단정하지 않는다. 1967년·2006년 수치는 부록 B의 원문을 확인한 뒤 인용한다.
